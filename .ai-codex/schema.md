## agent_registry (NocVault Agents Phase 2 — hub control plane, netvault 1.24.0)
Hub-owned canonical fleet registry; the data plane never touches these tables. `agents` is created FIRST (before the tables that reference it). Placed in schema.sql right after the app_settings seed block, before the safe-migration ALTERs.

agents  id(TEXT, PK — agt_… opaque) | name(TEXT, NOT NULL) | hostname(TEXT) | os(TEXT) | local_ip(TEXT) | site_id(INT — **soft ref to sites.id, NO FK** by design, resolved via LEFT JOIN at read time) | status(TEXT, NOT NULL, DEFAULT 'pending' — pending/online/degraded/offline/revoked; the API derives display status live, this column is the persisted hint) | agent_version(TEXT) | cert_fpr(TEXT — pinned identity fingerprint) | enrolled_at(TIMESTAMPTZ) | last_seen_at(TIMESTAMPTZ) | created_by(INT, no FK) | revoked_at(TIMESTAMPTZ) | created_at(TIMESTAMPTZ, NOT NULL, DEFAULT NOW()) | updated_at(TIMESTAMPTZ, NOT NULL, DEFAULT NOW())

agent_enrollment_tokens  token_hash(TEXT, PK — sha256 hex of the one-time token, never the raw token) | created_by(INT, no FK) | created_at(TIMESTAMPTZ, DEFAULT NOW()) | expires_at(TIMESTAMPTZ, NOT NULL) | preset(JSONB, NOT NULL, DEFAULT '{}' — {site_id, modules:[…]} applied on redeem) | used_at(TIMESTAMPTZ) | used_by(TEXT) — FK -> agents(id) ON DELETE SET NULL | note(TEXT)

agent_modules  agent_id(TEXT, PK part) — FK -> agents(id) ON DELETE CASCADE | app(TEXT, NOT NULL, PK part — 'logvault'|'ddivault'|'spanvault') | enabled(BOOLEAN, NOT NULL, DEFAULT TRUE) | config(JSONB, NOT NULL, DEFAULT '{}' — per-module work-plan)

agent_health  id(PK, BIGSERIAL) | agent_id(TEXT) — FK -> agents(id) ON DELETE CASCADE | ts(TIMESTAMPTZ, NOT NULL, DEFAULT NOW()) | cpu_pct(REAL) | mem_pct(REAL) | buffer_depth(INT) | module_status(JSONB — {logvault:'ok', ddivault:'auth_error', …}) — idx idx_agent_health_agent_ts on (agent_id, ts DESC)

Grants: the `netvault` app role + `nocvault_readonly` are covered by the tail blanket grants (GRANT ALL / GRANT SELECT ON ALL TABLES); an explicit `DO $$` block right after the table defs grants SELECT on the 4 tables to `claude_readonly` (which has no blanket grant in schema.sql). These tables hold NO secret columns (token_hash is a hash, cert_fpr a fingerprint), so no *_public exclusion view is needed. Verified in installer/Test-NocVault-Suite.ps1 via role-scoped has_table_privilege('netvault',…) on all 4 tables.

## View: v_devices_flat
Denormalized read view joining devices + brands + device_types + sites + countries + regions + vendors (3x: purchase/ma/support), created AFTER the safe-migration ALTERs so every selected column (mgmt_*, support_*, os_*, etc.) is guaranteed to exist first; read by lib/compliance.ts, lib/healthScore.ts, and device-listing API routes as the single flattened device query surface.

## setup.sql
One-time bootstrap seed (`INSERT INTO users ... ON CONFLICT (email) DO NOTHING`) that creates the default admin user (admin@yourcompany.com / super_admin); run once, manually, AFTER schema.sql on a fresh DB — not an ongoing migration script.

## Known schema debt
- `lib/eolEnrich.ts:96` and `:114` — `ensureEolSchema`'s runtime `CREATE TABLE IF NOT EXISTS` for `eol_discrepancies`/`eol_recommendations` still declares `device_id UUID`, while schema.sql:221 and :240 declare `device_id INTEGER` (explicit comment: "to match this schema's SERIAL devices.id"). schema.sql:309-320 ships a guarded `DO $$` retype migration specifically to repair this UUID→INTEGER drift on installs where the app's runtime self-heal ran before schema.sql — proof the two definitions have already diverged in the wild. If `ensureEolSchema` ever creates these tables first (e.g. app boots against a DB before schema.sql is applied), integer device ids inserted afterward would throw `invalid input syntax for type uuid` until schema.sql's fixup runs.
- `eol_seed.lifecycle` column — read/written throughout `lib/eolEnrich.ts` (`migrateLegacySeed`, `syncFromFeed`, `recomputeSeedKeys`: lines 68, 215-236, 358, 381, 401, 627, 794) and `lib/eolFeed.ts` (lines 63, 77, 144, 152, 161), added at runtime via `ALTER TABLE eol_seed ADD COLUMN IF NOT EXISTS lifecycle TEXT` (lib/eolEnrich.ts:68) — but schema.sql's `eol_seed` CREATE TABLE (182-195) and its "safe migration" ALTER block (279-305) never mention it. A DB provisioned by `psql -f schema.sql` alone does not have this column until the Node app runs once and self-heals it; a pure-SQL restore/clone workflow that skips app boot would be missing it.
- `eol_discrepancies.device_id` / `eol_recommendations.device_id` — soft FK only (INTEGER, no REFERENCES, "enforced at runtime" per schema.sql comment), no DB-level referential integrity. Mitigated in the device-delete path: `app/api/devices/[id]/route.ts` explicitly deletes matching rows from both tables before deleting the device (wrapped in try/catch since the tables may not exist on very old installs) — but any other code path that removes a device (bulk delete, direct SQL, a future route) would silently orphan rows unless it repeats the same manual cleanup.
- `installer/Install-NetVault.ps1` (the standalone, non-suite, legacy per-app installer — distinct from `Install-NocVault-Suite.ps1`) carries its OWN hand-written, hardcoded `$schemaSql` migration block (lines ~156-211) that duplicates a subset of schema.sql's ALTERs (vendors, user_sites, health_score_history, a handful of devices columns) but is missing entire tables schema.sql now has (user_apps, eol_seed, eol_enrichment_jobs, eol_discrepancies, eol_recommendations) and the support_* / os_* device columns. It does still run `setup.sql` and `schema.sql` is never invoked by this script directly — so a fresh install via this legacy path would produce a materially incomplete schema unless later reconciled. Flagging per CLAUDE.md's installer-parity rule since this script appears stale relative to schema.sql/Install-NocVault-Suite.ps1.

## Privilege notes
- Secret/credential-shaped columns: `users.password_hash` (bcrypt hash) and `app_settings.value` where `key='license_key'`. **The 2026-07 "FIXED" claim here was FALSE — corrected 2026-07-23.** The original fix's `app_settings_public` view selected `key, value, updated_at` — but NetVault's `app_settings` table has only `key`/`value` (no `updated_at`; that column exists on LogVault's/DDIVault's `app_settings`, and the view definition was copy-pasted from there). The `CREATE VIEW` failed at apply time; since `psql -f schema.sql` was not run with `ON_ERROR_STOP`, the script kept going into the REVOKE/GRANT `DO $$` block, which also referenced the never-created view and failed too — aborting that WHOLE block atomically (both tables, both roles), live-verified via `information_schema.role_table_grants`: `claude_readonly` still held plain `SELECT` on `users` and `app_settings`, and `app_settings_public` did not exist at all. **Now actually fixed:** `app_settings_public` selects only `key, value` (schema.sql:462-464); `nocvault_readonly`/`claude_readonly` no longer get table-level SELECT on `users` or `app_settings` — they read `users_public` (all columns except `password_hash`) and `app_settings_public` (an ALLOWLIST view: only `app_name`/`app_subtitle`/`app_logo_url`/`app_navy_color`/`app_primary_color`) instead. The REVOKE+view-GRANT step is now **two independent `DO $$` blocks, one per table** (schema.sql:471-484 for `users`, schema.sql:486-497 for `app_settings`) so a failure in one can no longer silently roll back the other; each has an `EXCEPTION WHEN OTHERS` handler that `RAISE WARNING`s loudly (naming the exposed column) instead of swallowing the error. `installer/Update-NetVault.ps1` and `installer/Install-NocVault-Suite.ps1`'s NetVault step now also invoke `psql` with `-v ON_ERROR_STOP=1`, so a future genuine SQL error (unlike this one) stops the apply instead of silently "succeeding" — idempotent statements (`IF NOT EXISTS`/`IF EXISTS`/`OR REPLACE`/`ON CONFLICT`) are unaffected since they're not errors on a re-run. A new `users` column or `app_settings` key still defaults to HIDDEN from these two roles until deliberately added to the matching view.
- schema.sql applies its own inline grants in two DO $$ blocks: one (schema.sql:383-407) grants ALL PRIVILEGES + reassigns table/sequence/view ownership to the `netvault` role (needed because the installer runs schema.sql as the `postgres` superuser, so without this every object would be owned by postgres and the app's runtime DDL, e.g. `ensureEolSchema`'s ALTERs, would fail with "must be owner of table"); the other (schema.sql:418-426) grants USAGE+SELECT to `nocvault_readonly` plus `ALTER DEFAULT PRIVILEGES FOR ROLE netvault ... GRANT SELECT ... TO nocvault_readonly` so tables the app creates at runtime (eol_seed, eol_enrichment_jobs, eol_discrepancies, eol_recommendations) are auto-covered without a separate grant step. Two more blocks (schema.sql:471-497, corrected 2026-07-23, see above) are the `users_public`/`app_settings_public` fix — **placed AFTER the blanket grant on purpose**: a table-level `GRANT SELECT` overrides any earlier column/view-level restriction in Postgres, so the narrowing fix only holds if it's the LAST statement touching that role's privileges.
- Confirmed no separate `schema-grants.sql` file exists anywhere in the repo (checked `scripts/` — only `cleanup-brand-in-model.sql` and `gen-eol-seed.cjs` — and `installer/`, which has no such file either). All grants are either inline in schema.sql or inline PowerShell `psql -c "GRANT ..."` calls in the installer scripts.
- Installer flow (updated 2026-07): `Install-NocVault-Suite.ps1` now calls `GrantNocRoRead "<db>"` for each app **BEFORE** that app's `schema.sql` runs, not after. Previously it ran after (line ~393 for netvault, and the equivalent per-app spot for logvault/ddivault/spanvault), which meant `GrantNocRoRead`'s own unconditional blanket `GRANT SELECT ON ALL TABLES` executed AFTER schema.sql's narrowing fix and silently undid it on every fresh suite install — `GrantNocRoRead` only grants `nocvault_readonly`, never `claude_readonly`, so that half of the fix was never at risk, but the Hub's own cross-DB role was re-exposed to every secret table on day one of any new customer install. Reordering fixes this: whichever grant runs last wins, and schema.sql (now running after `GrantNocRoRead`) always ends with the correct narrow grant. Running `GrantNocRoRead` before any table exists is safe — `GRANT SELECT ON ALL TABLES` on zero tables is a no-op, and its `ALTER DEFAULT PRIVILEGES` only auto-grants SELECT on tables about to be created, which schema.sql's own later REVOKE still correctly narrows regardless of how the grant first landed. `Update-NetVault.ps1` re-applies `schema.sql` as `postgres` on every update (lines 236-269) specifically to pick up new views/grant self-heal blocks — a ROUTINE update was never actually at risk from this bug (it only ever calls `schema.sql` directly, never `GrantNocRoRead`), only a FRESH suite install was. Gated on `POSTGRES_PASSWORD` being present in `.env` (soft-skips with a warning on pre-existing installs that predate that key — non-fatal). The legacy standalone `Install-NetVault.ps1` does NOT invoke schema.sql at all — see Known schema debt above.
